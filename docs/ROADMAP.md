**No validado — limitación del entorno que generó el scaffold, no del código:** build real de las 5 imágenes Docker y arranque end-to-end de los contenedores, porque ese entorno no tenía acceso de red a Docker Hub ni el SDK de .NET 10 instalado. **Primera acción recomendada al retomar en un entorno con Docker Desktop/SDK real: `make up && make smoke`** y corregir lo que la validación estática no pudo anticipar (típicamente: pequeños ajustes de healthcheck o versión de imagen).
**Deliberadamente fuera de esta fase:** stack de observabilidad (FASE 2), seeding real (`scripts/seed` es un placeholder que falla explícitamente), usuarios Mongo con privilegio mínimo (FASE 4+). Detalle completo de cada decisión y su trade-off en `infrastructure/docker/README.md`.

**Corrección (2026-08-16, al iniciar FASE 2):** el entorno que retomó el trabajo sí tenía Docker Desktop y el SDK de .NET 10, y la validación real expuso 3 defectos pre-existentes de este scaffold (nunca compilados hasta ahora): (1) `Ppip.BuildingBlocks.Health.csproj` no referenciaba el shared framework de ASP.NET Core, por lo que `HealthCheckResult`/`IHealthCheck` no resolvían; (2) las 3 registraciones `AddCheck(name, sp => new HttpEndpointHealthCheck(...), tags)` usaban una sobrecarga de `AddCheck` que no existe (se corrigió a `AddTypeActivatedCheck<T>`); (3) los 4 Dockerfiles no copiaban `src/Directory.Build.props`/`src/global.json`, dejando `TargetFramework` vacío dentro del contexto de build, y creaban un usuario `appuser` con UID 1654 que colisiona con el usuario `app` que ya trae la imagen base `mcr.microsoft.com/dotnet/aspnet:10.0`. Los 3 se corrigieron como parte de FASE 2 (no eran parte del alcance nuevo, pero bloqueaban validar cualquier cosa). Las 5 imágenes compilan y los 4 servicios .NET compilan limpio (`dotnet build`) tras la corrección.

## Nota de cierre de FASE 2 (2026-08-16)

Implementado y validado con Docker Desktop + .NET 10 SDK reales (a diferencia de FASE 1, este entorno sí tenía ambos): perfil `obs` en `docker-compose.yml` (OTel Collector, Prometheus, Loki, Tempo, Grafana — 5 servicios, red `obs`); `Ppip.BuildingBlocks.Observability` (traces+métricas+logs vía OTLP al Collector, `CorrelationIdMiddleware` + `CorrelationIdDelegatingHandler` per docs/06-api/00) referenciado desde los 4 servicios .NET; endpoint temporal `GET /api/diagnostics/trace-check` en Platform API que llama a los 3 workers para demostrar el trace end-to-end exigido por el criterio de éxito de la fase; dashboard `PPIP - Service Overview` provisionado en Grafana; decisión Tempo vs Jaeger resuelta a favor de Tempo (ADR-011 Amendment). 4 tests unitarios xUnit para `CorrelationIdMiddleware` (`tests/Ppip.BuildingBlocks.Observability.Tests`) — detectaron y permitieron corregir 2 bugs reales antes de integrar (header en blanco no se generaba de nuevo; el header de respuesta se fijaba vía `OnStarting`, que no se dispara de forma fiable sin un servidor real).

Validar el stack completo levantado expuso 3 defectos adicionales, también corregidos: (4) `Makefile`/`scripts/smoke-test.sh` invocaban `docker compose` con `-f docker-compose.yml` explícito, lo que **desactiva** el auto-descubrimiento de `docker-compose.override.yml` — los puertos de desarrollo (Mongo, Redis, RabbitMQ, MinIO, Qdrant, Ollama y ahora Grafana/Prometheus/Loki/Tempo) nunca se habían publicado realmente en el host desde FASE 1; se agregó el segundo `-f` explícito en ambos scripts. (5) `prometheus.yml` sin `honor_labels: true` hacía que Prometheus renombrara la label `job` real (nombre del servicio) a `exported_job` por colisión con la del propio `scrape_config` — se corrigió, y ahora `job` distingue cada servicio tal como espera el dashboard. (6) `datasources.yaml` de Grafana: el campo `url` del derived field de Loki (`${__value.raw}`) se guardaba vacío porque el provisioner de Grafana expande `$VAR`/`${VAR}` como variables de entorno al leer el YAML; se corrigió escapando a `$${__value.raw}`.

**Validado end-to-end, con el stack completo arriba (`docker compose up -d`, perfiles `core`+`app`+`obs`, 18 contenedores) en este mismo entorno:** las 17 imágenes relevantes healthy (Traefik quedó en `Created` — puerto 80 ya ocupado en este host por otro proceso, conflicto del entorno local, no del compose); `GET /api/diagnostics/trace-check` devolvió 200 con los 3 workers healthy; el mismo `traceId` apareció con sus 7 spans completos (4 en Platform API, 1 por worker) consultando la API HTTP de Tempo directamente; el mismo `correlationId`+`traceId` aparecieron en los logs estructurados de Loki (`job=ppip-platform-api`); Prometheus mostró `http_server_request_duration_seconds_count` separado por `job` para los 4 servicios; Grafana provisionó los 3 datasources (con correlación Loki↔Tempo↔Prometheus) y el dashboard `PPIP - Service Overview` con sus 5 paneles.
**Deliberadamente fuera de esta fase (recorte explícito):** los 4 dashboards de negocio (dependen de métricas `ppip_*` que no existen hasta sus fases — FASE 6/8/9-10); alertas iniciales (misma razón); propagación de correlationId en eventos RabbitMQ (ningún worker publica eventos reales todavía). Detalle en `docs/13-observability/01-observability-spec.md`.

## Nota de cierre de FASE 3 (2026-08-16)

Implementado: realm Keycloak `ppip` (`infrastructure/docker/config/keycloak/ppip-realm.json`) con los 5 roles de ADR-010+Amendment como **roles compuestos** (Keycloak resuelve `admin` ⊇ `editor` ⊇ `analyst` ⊇ `viewer`, sin lógica de rango en .NET); cliente `ppip-spa` (público, PKCE, para FASE 16) y `ppip-test-client` (confidencial, Direct Access Grants, solo para tests automatizados); `Ppip.BuildingBlocks.Security` (`KeycloakAuthenticationExtensions`, `PpipRoles`) referenciado desde Platform API; 2 endpoints de diagnóstico protegidos (`whoami` en `viewer`, `trace-check` en `analyst`); rate limiting por IP + security headers en Traefik, atados por fin al router de `platform-api` (existían desde FASE 1 sin usar). 12 tests xUnit (`tests/Ppip.PlatformApi.Tests`) contra un Keycloak real (Testcontainers, mismo `ppip-realm.json`), no un doble.

**Esta fase, más que ninguna otra hasta ahora, dependió de validar contra infraestructura real** — encontró y corrigió 3 defectos no obvios que ninguna revisión estática habría detectado:
1. **Roles vacíos al autenticar por password grant:** Keycloak 26 evalúa "required actions" dinámicamente en cada login (no solo lo guardado en el usuario) — el required action `VERIFY_PROFILE`, activo por defecto, exige `firstName`/`lastName` si el realm los declara obligatorios; los usuarios de prueba no los tenían y el login fallaba con "Account is not fully set up" (`resolve_required_actions`). Se agregaron `firstName`/`lastName`/`emailVerified: true`/`requiredActions: []` explícitos a los 5 usuarios del realm.
2. **Validación de issuer siempre fallaba pese a que Authority/Issuer coincidían exactamente:** `AddPpipKeycloakAuth` leía `builder.Configuration` de forma síncrona en el momento en que `Program.cs` la invoca — en tests con `WebApplicationFactory`, ese momento es **anterior** a que el override de `ConfigureAppConfiguration` del test se aplique, así que el delegate capturaba cadenas vacías aunque `IConfiguration` ya reflejara el valor correcto más tarde (confirmado imprimiendo ambos). Se corrigió configurando `JwtBearerOptions` de forma perezosa vía `AddOptions<T>().Configure<IConfiguration>(...)`, que se resuelve con la configuración ya completamente mezclada. De paso también se dejó un `IssuerValidator` explícito en vez de `ValidIssuer`: `JwtBearerHandler` solo combina (`Concat`) el issuer autodescubierto del documento OIDC con `ValidIssuers` si esa colección ya era no-nula — dejarla en null la reemplaza silenciosamente.
3. **JWKS inalcanzable en el flujo real de docker-compose (aunque los tests con Testcontainers pasaban):** Keycloak (`KC_HOSTNAME_STRICT=false`) embebe su `KC_HOSTNAME` externo (`auth.ppip.localhost`) en `issuer`/`jwks_uri` del discovery document sin importar por qué DNS se lo consultó — y clientes HTTP (curl lo confirma; probablemente también el stack HTTP de .NET) resuelven cualquier host `*.localhost` **siempre** a loopback (RFC 6761), ignorando DNS. Platform API terminaba "descubriendo" el JWKS... de sí mismo. Se corrigió en dos frentes: (a) alias de red `auth.${PPIP_DOMAIN}` en el servicio `keycloak` (`app` network) para que el nombre resuelva vía DNS de Docker; (b) un `ConnectCallback` en `SocketsHttpHandler` que fuerza la conexión física de todo el backchannel de JwtBearer al `host:puerto` real de `Authority`, sin importar qué URL venga en el documento de descubrimiento — robusto independientemente de por qué exactamente el hostname no resolvía.

**Validado end-to-end contra el stack real** (no solo Testcontainers): con los 5 usuarios de prueba, `whoami`(viewer) → 200 para los 5 roles; `trace-check`(analyst) → 403 para `viewer.test`, 200 para `analyst.test`/`editor.test`/`admin.test`/`superadmin.test` (confirma la composición de roles); sin token → 401 en ambos; `admin.test` trae `roles:["viewer","editor","admin","analyst"]` en la respuesta (composición Keycloak, no lógica .NET).
**Deliberadamente fuera de esta fase (recorte explícito):** client credentials para workers (ADR-010 — ningún worker tiene todavía un endpoint interno que llamar con su propia identidad); rate limiting por usuario autenticado (solo por IP por ahora); integración OIDC del SPA Angular (FASE 16); FileValidator/allowlist SSRF (FASE 7, Document Worker no descarga nada real aún). Detalle en `docs/12-security/01-security-controls.md`.

## Nota de cierre de FASE 5 (2026-08-16)

**Spike ejecutado contra la API real** (el usuario proporcionó un ticket personal de uso limitado, protegido en `infrastructure/docker/.env`, nunca commiteado — verificado antes de cada commit). Solo 2 llamadas reales deliberadas (1 listado + 1 detalle) más 1 error real encontrado sin buscarlo — el resto de los escenarios de error se cubren con los ejemplos JSON literales de la Guía de Uso oficial (no hacía falta gastar cuota reproduciéndolos).

**Contrato real descubierto — Guía de Uso API Compra Ágil v2, v3.0 (mayo 2026):** base URL `https://api2.mercadopublico.cl`; autenticación vía **header** `ticket` (no query param, corrigiendo una suposición inicial de esta misma sesión basada en resúmenes de búsqueda web — el PDF oficial fue la fuente que lo resolvió); dos endpoints (`GET /v2/compra-agil` listado paginado, `GET /v2/compra-agil/{codigo}` detalle); **cuota diaria por ticket** (no rate limit por minuto — corrige ASM-07), reset a medianoche, 429 cuando se agota.

**Implementado:** `Ppip.Procurement.Infrastructure` (nuevo módulo, `src/modules/procurement/`): `IChileCompraClient` + `ChileCompraHttpClient` resiliente (`Microsoft.Extensions.Http.Resilience`/Polly — 3 intentos, backoff 1s/5s/25s, circuit breaker 5 fallos/30s→60s, **429 excluido a propósito del retry automático** porque es una cuota diaria agotada, no una falla transitoria — reintentar en segundos sería inútil); DTOs completos de list+detail; `ChileCompraDateParser` (normaliza los dos formatos de fecha reales, ver discrepancias abajo); `CompraAgilListQuery` con validación de los filtros documentados. 22 contract tests (`Ppip.Procurement.Infrastructure.Tests`) vía WireMock.Net contra fixtures reales grabadas (`tests/Ppip.Procurement.Infrastructure.Tests/fixtures/`, con README explicando la procedencia exacta de cada una — reales, literales de la documentación, o construidas).

**Discrepancias reales vs. la documentación oficial, encontradas por el spike (ninguna evidente sin probar contra la API real):**
1. **Mínimo de `tamano_pagina` no documentado.** La guía solo documenta el máximo (50); `tamano_pagina=5` devuelve 400 con `"tamano_pagina debe estar entre 10 y 50"` — el mínimo real es 10. Encontrado en el primer intento del spike, sin buscarlo.
2. **Formato de fecha inconsistente entre e incluso dentro del mismo endpoint.** `fechas.fecha_ultimo_cambio` del listado llega en ISO-8601 con milisegundos (`"2026-08-16T23:05:02.410Z"`), pero `fechas.fecha_publicacion`/`fecha_cierre` del **mismo objeto** llegan en formato corto sin zona horaria (`"2026-08-16 23:02"`) — y el detalle usa el formato corto también para `fecha_ultimo_cambio` (el mismo campo, otro formato, según el endpoint). Los DTO guardan fechas como `string` crudo a propósito; `ChileCompraDateParser` normaliza ambos formatos cuando la capa de aplicación (FASE 6) los necesite como `DateTimeOffset`.
3. **`id_orden_compra` aparece como campo raíz del payload**, no anidado bajo `orden_compra.*` como documenta la guía (que además admite en su propio changelog v3.0 una "corrección de campos orden_compra" reciente — es un contrato que la propia ChileCompra sigue estabilizando). El ejemplo capturado no tenía OC emitida; confirmar la forma exacta cuando exista OC queda para FASE 6.
4. **Campos documentados como `string` llegan como número JSON.** `documentos[].id` (documentado como UUID string) y `productos_solicitados[].codigo_producto` (documentado como `int|string` mixto, confirmado numérico) — se agregó `FlexibleStringConverter` para aceptar ambos sin romper la deserialización.

**OQ-01 y OQ-10 cerradas; OQ-06/ASM-08 parcialmente informadas** (el usuario aceptó los términos de uso al pedir el ticket — revisión legal formal del alcance sigue pendiente, no es analizable por ingeniería); **OQ-09 parcialmente informada** (`codigo_producto` tiene forma compatible con UNSPSC, sin confirmar contra catálogo oficial); **OQ-02 sigue abierta** (se confirmó que existen documentos adjuntos reales con id numérico + nombre de archivo, pero no se probó ningún endpoint de descarga — eso es el spike de FASE 7). Detalle completo de las 4 preguntas/supuestos en `docs/01-discovery/09-open-questions.md` y `docs/01-discovery/07-assumptions.md`.

**Deliberadamente fuera de esta fase (recorte explícito):** `SyncOrchestrator`/anti-corruption layer que mapea estos DTOs a los agregados de `Ppip.Procurement.Domain` (FASE 6 — este cliente devuelve DTOs crudos a propósito, sin tocar el dominio); adaptador real de descarga de documentos (FASE 7, y depende de que se cierre OQ-02); spike de la API de Órdenes de Compra para completar el cruce vía `id_orden_compra` (se hace cuando FASE 6 lo necesite, no antes).
